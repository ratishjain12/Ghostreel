Eight Patterns That Make AI Agents Work

“Most AI agents are just a for loop with a prompt.”
A written walkthrough of the eight patterns that turn that loop into something that actually works — four ways a single agent decides what to do next, and four ways multiple agents get organized to work together. Each one gets a short code example and the concrete way it breaks when built carelessly.

Introduction

Most AI agents are, underneath, just a for loop with a prompt. What separates the ones that actually work from the ones that don't is which of a small set of patterns they're built on. There are eight of them.

The first four are things a single agent does on its own — how it decides to use a tool, how it reasons about what to do next, whether it plans ahead or adapts step by step, and how it handles retrieval. The last four are about organizing more than one agent together — running them in sequence, running them at once, routing work between them, or putting one in charge of the rest.

Single-Agent Patterns

1.Tool Use

The model doesn't call functions directly. Instead, it emits a structured call, the surrounding code runs it, and the result goes back in as a new message for the model to continue from.

Example
tools = [{
    "name": "get_weather",
    "description": "Get current weather for a city",
    "parameters": {"type": "object",
                   "properties": {"city": {"type": "string"}},
                   "required": ["city"]},
}]

response = model.chat(messages, tools=tools)
if response.tool_call:
    result = execute_tool(response.tool_call.name, response.tool_call.arguments)
    messages.append({"role": "tool", "name": response.tool_call.name, "content": result})
    response = model.chat(messages, tools=tools)  # model sees the result, continues
Failure case

The model emits a tool call that looks well-formed but has a bad argument (a city that doesn't exist, a required field silently missing). If execute_tool isn't validated against the tool's own JSON Schema before it runs, that either crashes the tool or executes with a wrong default. Validate every call against its schema before executing, and return a structured error back to the model instead of letting it crash.

2.ReAct

Reason, then act, then observe, and repeat. The reasoning and the acting are interleaved rather than done once up front, because you can't know what to search next until you've seen what the last search returned.

Example
scratchpad = []
for step in range(MAX_STEPS):
    thought = model.chat(prompt + format_scratchpad(scratchpad))
    if thought.is_final_answer:
        return thought.answer
    observation = execute_tool(thought.action)
    scratchpad.append((thought, observation))
raise MaxStepsExceeded()
Failure case

With no step cap (or one set too high), the model gets stuck in a "search — still not sure — search again" loop that never terminates, silently burning cost and latency. Set a hard step cap, and give the model an explicit fallback for when it's hit, instead of failing with nothing.

3.Plan & Execute

One model plans every step upfront, then the plan just gets run. It's more predictable than ReAct, but less adaptive — the plan doesn't change once execution starts.

Example
plan = planner_model.chat(f"Break this task into ordered steps: {task}")

results = []
for step in plan.steps:
    results.append(executor_model.chat(step, context=results))

return synthesize(results)
Failure case

Step 3's real result invalidates an assumption step 5 was planned under — say step 3 discovers the data source is empty, but step 5 still assumes a hundred rows. Because nothing re-plans mid-execution, the agent marches on with a broken plan. Add a cheap check before each step — does its assumption still hold? — with a bailout to re-plan when it doesn't.

4.Agentic RAG

The model decides if it even needs to retrieve, what to search for, and whether the results it gets back are good enough before it answers — retrieval becomes a decision the model makes, not a fixed step that always runs.

Example
def answer(query):
    if not model.needs_retrieval(query):
        return model.answer(query)

    for attempt in range(MAX_RETRIES):
        docs = retrieve(model.formulate_search(query))
        if model.judge_sufficient(docs, query):
            return model.answer(query, context=docs)
        query = model.reformulate(query, docs)

    return model.answer(query, context=docs)  # best effort
Failure case

The "is this sufficient?" judgment is made by the same model, on the same weak evidence, with no independent signal to check it against — a model confidently wrong about relevance approves bad chunks and the retry loop never improves anything. Pair the model's judgment with a cheap, independent check (a relevance score threshold), not its own confidence alone.

Multi-Agent Patterns

5.Sequential

Agents run in a fixed pipeline — draft, review, format — with each one's output feeding directly into the next.

Example
draft = draft_agent.run(task)
reviewed = review_agent.run(draft)
final = format_agent.run(reviewed)
Failure case

The review agent flags the draft as wrong, but the pipeline has no branch for that — it passes the rejected draft straight to the format agent anyway, because each stage only knows "hand off to the next stage," not "handle a rejection." Give every stage an explicit pass/fail contract, and let a failure route back to an earlier stage.

6.Parallel

Independent agents run at the same time on different pieces of the task, and their outputs get merged once they're all done.

Example
results = await asyncio.gather(
    agent_a.run(source_1),
    agent_b.run(source_2),
    agent_c.run(source_3),
    return_exceptions=True,
)
final = merge_agent.run(results)
Failure case

Without return_exceptions=True (or a per-task try/except), one source timing out can fail the entire batch — or the merge agent receives a result it was never built to handle and silently produces a worse answer. Have the merge step explicitly handle a missing source rather than assume all of them always succeed.

7.Router

One agent classifies the task, then sends it to whichever specialist agent actually handles that kind of work.

Example
category = router_model.classify(task, labels=["billing", "technical", "account"])
agent = {
    "billing": billing_agent,
    "technical": tech_agent,
    "account": account_agent,
}[category]
return agent.run(task)
Failure case

A genuinely ambiguous task — half billing, half technical — gets forced into one bucket by the classifier, so the wrong specialist handles it confidently and wrong. Have the router return a confidence score, and route low-confidence cases to a generalist instead of forcing a bucket.

8.Orchestrator-Worker

A manager agent breaks the task down, assigns the pieces to workers, checks their results, and decides what happens next.

Example
remaining, done = manager.decompose(task), []
while remaining:
    subtask = remaining.pop(0)
    result = worker_pool.assign(subtask)
    if manager.check(result):
        done.append(result)
    else:
        remaining.insert(0, manager.revise(subtask, result))
return manager.finalize(done)
Failure case

manager.revise keeps producing a slightly different but equally-failing subtask, so the worst case is an infinite retry loop stuck on one subtask while the rest of the plan waits, with no error ever surfaced. Cap retries per subtask, and escalate — skip it with a flagged gap, or hand it to a human — instead of retrying forever.

Key Takeaways

These eight patterns are the actual building blocks behind agents that work:

  • Tool Use — the model requests a call, your code runs it, the result comes back as a message.
  • ReAct — reason, act, observe, repeat, because the next step depends on the last result.
  • Plan & Execute — plan every step upfront, then run the plan; predictable over adaptive.
  • Agentic RAG — the model decides whether, what, and how much to retrieve before answering.
  • Sequential — a fixed pipeline of agents, each output feeding the next.
  • Parallel — independent agents run at once, then their outputs are merged.
  • Router — one agent classifies and hands off to the right specialist.
  • Orchestrator-Worker — a manager decomposes, assigns, checks, and decides what's next.

Most agents that fall apart in production aren't missing a clever prompt — they're missing one of these eight patterns.
