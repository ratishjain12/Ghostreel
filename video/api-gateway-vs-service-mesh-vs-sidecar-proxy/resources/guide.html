The front door, the hallways, and the local layer in between — why a microservices system usually needs all three, not just one.
Gateway — the edge Sidecar — per service Mesh — coordinated

API gateway, service mesh, sidecar proxy — all three sit in the request path of a microservices system, and it's easy to think you only need one. You usually need all three, doing different jobs.

1The API Gateway

The single door for external traffic

An API gateway sits at the edge — the single door external clients come through. It's the one place handling auth, rate limiting, and routing requests to the right service, before anything is internal traffic yet.

2The Sidecar Proxy

A local traffic layer for one service

A sidecar proxy is a small proxy deployed next to a single service instance, intercepting everything that service sends and receives. It's not about the edge — it's about every individual service having its own local traffic layer.

3The Service Mesh

Sidecars, coordinated by a control plane

A service mesh is what you get when every service has its own sidecar, and a control plane manages all of them together — retries, timeouts, encryption, and observability, for every service-to-service call, consistently, without each team building it themselves.

Front door vs. hallways

The gateway handles traffic coming into your system from outside. The mesh, built out of sidecars, handles traffic moving between your own services once it's already inside.

In one line

One's the front door, the other is the hallways.

When to add each one

  • Add an API gateway as soon as external clients talk to more than one backend service.
  • Add a service mesh once you have enough internal services that retries, mTLS, and observability between them can't be handled per-team anymore.

Key takeaways

Gateway

The front door. Edge-facing: auth, rate limiting, routing for external clients.

Sidecar

A local traffic layer riding next to a single service instance.

Mesh

Sidecars plus a control plane, coordinating retries, timeouts, encryption, and observability across every internal service-to-service call.

Same request path, three different jobs — a gateway guarding the door, a sidecar riding with each service, and a mesh tying every sidecar together into one coordinated layer.
