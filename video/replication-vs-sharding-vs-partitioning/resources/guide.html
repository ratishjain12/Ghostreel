Systems / Databases: Quick Guide

Replication, Sharding, Partitioning

Three answers people give to "how do we scale the database." They get treated like one decision, when they're actually three different problems wearing overlapping names. Here's what each one actually fixes, and when to reach for which.

00 · SetupWhy these three get lumped together

Say you need to scale the database, and someone will suggest replication, partitioning, and sharding like they solve the same problem.

They don't. Each one addresses a different failure mode, and knowing which one you actually need is the difference between fixing the bottleneck and just adding infrastructure.

01 · Copy everywhereReplication

Replication copies your entire dataset onto multiple servers. Every replica has the same data.

What it's for

Availability and read scale. If one node dies, another has everything, and you can spread reads across all of them.

02 · Split, don't copyPartitioning

Partitioning does the opposite of replication. Instead of copying everything everywhere, you split your data into smaller chunks, by date range, by customer ID, whatever, so no single piece gets too big to manage.

What it's for

It doesn't add copies, it divides the original.

03 · Partitioning, one level furtherSharding

Sharding is partitioning taken one level further. Each partition doesn't just live on a different table, it lives on a completely different database server.

What it's for

Now write load is split across machines too, not just read load.

04 · The thesisDifferent problems, not interchangeable

Replication solves "what if one server dies or gets too many reads." Partitioning and sharding solve "what if the dataset itself is too big for one server to hold or write to."

ApproachWhat it actually solves
ReplicationA server dying, or too many reads for one server to handle.
PartitioningA dataset too big for one table to hold or query efficiently.
ShardingA dataset too big for one server to hold, and write throughput too high for one server to handle.

Different problems, often used together, never interchangeable.

05 · Decision guideWhen to reach for which

  • Replication Add it first: almost every production database needs it for availability alone.
  • Partitioning Reach for it when a single table gets too large to query efficiently.
  • Sharding Reach for it when write throughput on a single server becomes the actual bottleneck.

RecapTakeaways

  1. Replication copies the entire dataset onto multiple servers: every replica holds the same data, for availability and read scale.
  2. Partitioning divides the original dataset into smaller chunks instead of copying it, so no single piece gets too big to manage.
  3. Sharding is partitioning taken further: each partition lives on its own database server, so write load is split across machines too.
  4. Replication answers "what if one server dies or gets too many reads." Partitioning and sharding answer "what if the dataset itself is too big for one server to hold or write to."
  5. Add replication first, partition when a table gets too large to query, shard when write throughput on a single server becomes the bottleneck.
