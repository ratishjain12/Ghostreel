Idempotency key vs deduplication vs distributed lock

Three ways to stop the same thing from happening twice, solving three genuinely different problems.

idempotency key deduplication distributed lock

Why these three keep getting confused

Idempotency key, deduplication, and distributed lock are three ways to stop the same thing from happening twice, but they solve three genuinely different versions of that problem. Mixing them up usually means reaching for the wrong tool at the wrong layer of the system.

01 · client sideIdempotency key

An idempotency key is something the client attaches to a request: a unique ID for that specific logical operation. If the same request gets sent twice, because of a retry, a flaky network, or something else entirely, the server sees the same key and knows to return the original result instead of doing the work again.

02 · consumer sideDeduplication

Deduplication is the system's own job, not the client's. It's for event and message pipelines, where the same message can arrive more than once through no fault of the sender, and the consumer has to recognize it's already processed that exact message ID and skip it.

03 · concurrency, not duplicatesDistributed lock

A distributed lock isn't really about duplicates at all. It's about concurrency: it makes sure that when multiple processes across multiple machines could all try to do the same critical section of work at the same time, only one of them actually gets to.

How the three relate

Idempotency keys and deduplication both stop the same operation from running twice: one from the client side, one from the consumer side. A distributed lock stops different processes from colliding while doing that operation in the first place.

Idempotency key
Client-side. Same request, sent twice by the same caller (retry, flaky network) → server returns the original result instead of repeating the work.
Deduplication
Consumer-side. Same message, delivered twice by the pipeline (at-least-once delivery) → consumer recognizes the message ID and skips it.
Distributed lock
Cross-process. Different workers, same critical section, same moment → only one is allowed to proceed.

Choosing the right tool

Match the mechanism to where the duplication risk actually lives:

  • Idempotency key: for any client-initiated write that might get retried, payments especially.
  • Deduplication: for any message or event pipeline where at-least-once delivery is possible.
  • Distributed lock: for when multiple workers could pick up the same job simultaneously and you need exactly one of them to win.

Key takeaways

  1. Idempotency key, the client's guard against its own retries.
  2. Deduplication, the system's guard against duplicate delivery it didn't cause.
  3. Distributed lock, the guard against two processes racing into the same critical section at once.
  4. The first two protect against repeating an operation. The third protects against colliding while performing it.
