Retry, Circuit Breaker, Fallback: The Real Sequence

Three resilience patterns that show up together in almost every distributed system, and get used like they're one thing. They actually fire at completely different moments.

Retry, circuit breaker, and fallback are three resilience patterns that show up together in almost every distributed system, and get treated like they're interchangeable. They're not. Each one fires at a completely different moment in a failure, and understanding that sequence is the difference between resilience that actually works and resilience that just looks good in a design doc.

Pattern 1

The Retry

A retry just tries again. A request fails, you wait a bit, maybe with backoff, and send it again, betting that the failure was transient: a blip, not a real outage.

Pattern 2

The Circuit Breaker

A circuit breaker is what stops you from retrying forever into a dependency that's actually down. It watches the failure rate, and once it crosses a threshold, it trips, blocking new requests to that service entirely for a cooldown period.

It protects the failing service from being hammered, and it protects you from wasting time on calls that will fail anyway.

Pattern 3

The Fallback

A fallback is what you do instead, once retry has given up or the breaker is open. Return cached data, a default value, a degraded response, anything that keeps the system usable instead of returning an error.

The Real Sequence

Put together, the three patterns cover three different jobs in the same failure:

  • Retry handles the blip.
  • Circuit breaker handles the outage.
  • Fallback handles what the user actually sees while all of that is happening.

When to Add Each One

  • Retry

    Add retries for calls that can genuinely fail transiently, like a flaky network blip.

  • Circuit Breaker

    Add a circuit breaker around any dependency that can go down for real, so you're not making things worse.

  • Fallback

    Add a fallback wherever a failure would otherwise be user-facing.

Key Takeaways

  • Retry, circuit breaker, and fallback solve different problems: they aren't three names for the same idea.
  • Retry assumes the failure is temporary. Circuit breaker assumes it might not be, and stops you from making it worse.
  • Fallback is the only one of the three that the user actually experiences directly.
  • Match each pattern to what it's actually for: transient blips get retries, real outages get a breaker, user-facing failures get a fallback.
